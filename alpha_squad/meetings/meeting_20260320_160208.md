### 1. 105feat의 근본적 문제

현재 105feat 구조를 보면 **OHLCV 쌍 10종 × 윈도우 5종 = 50개 가격 차이 feature**가 핵심입니다. 여기서 즉시 보이는 문제:

**공선성이 심각합니다.** `close-open` 윈도우 1분과 `close-open` 윈도우 5분은 상관계수 0.8 이상일 겁니다. 153feat 분석에서도 "153→~50 effective features"라는 결과가 나왔죠. 105feat도 마찬가지로 절반 이상이 redundant할 가능성이 높습니다.

**거래량 정규화가 cross-sectional 오염원입니다.** `vol_per_avg` (윈도우 1/5/30/120/360분)은 종목 내 temporal ratio라 괜찮지만, `quote_asset_vol_normalized`는 어떤 base로 정규화했는지가 핵심입니다. 만약 전체 종목 대비 비율이면 대형/소형 구분 인코딩이 되어 CS-MLP에서 beta를 학습하게 됩니다.

---

### 2. Non-Top200에서 AG가 되고 CS-MLP가 안 되는 이유 — 피처 관점

AG CLS는 **종목별 독립 학습**이니까 `vol_per_avg_360`이 "이 종목의 평소 대비 거래량"을 의미합니다. CS-MLP는 같은 피처가 "전체 종목 중 이 종목의 상대적 거래량"으로 읽힙니다. **같은 피처인데 모델에 따라 의미가 달라지는 겁니다.**

---

### 3. H1-1 (TabM + 105feat per-sample) 비판

TabM의 PLE binning이 스케일을 흡수한다는 가설은 맞습니다. **하지만 105feat 중 `price_increase_per_decrease` (윈도우 30/120/360분)은 ratio feature라 non-stationary합니다.** 소형주는 이 ratio가 극단적으로 움직이고, 대형주는 안정적입니다. PLE binning이 이걸 흡수하려면 bin 수가 충분해야 하는데, n_bins=48이면 소형주 꼬리 분포가 잘릴 수 있습니다.

**대안**: `price_increase_per_decrease` 대신 **`up_ratio = count(ret>0) / window`**로 바꾸면 bounded [0,1]이 되어 스케일 문제가 사라집니다.

---

### 4. H3 (Temporal z-score) — 이것이 핵심

**가장 유망한 방향입니다.** 이유:

- 종목별 rolling z-score는 "이 종목의 최근 N분 대비 현재 상태"를 인코딩
- regime 변화에 robust — rolling window가 자동으로 적응
- cross-sectional 오염 없음

**하지만 look-ahead bias 체크 필수입니다.** rolling z-score의 window size가 예측 horizon(120분)보다 짧으면 label과 overlap 가능성이 있습니다. **window ≥ 240분 (2시간) 이상을 권장합니다.**

---

### 5. 빠진 피처 — 제가 추가 제안

1. **Garman-Klass volatility**: OHLC만으로 계산 가능, 단순 `(H-L)/C`보다 효율적인 변동성 추정. Non-Top200 소형주의 변동성 regime을 잡을 수 있음.

2. **Amihud illiquidity ratio** = `|ret| / volume`: 소형주일수록 높음. 이게 피처로 들어가면 모델이 유동성 risk를 학습할 수 있음. **단, 이것도 cross-sectional로 쓰면 대형/소형 분류기가 됩니다. 반드시 종목별 rolling rank나 temporal z-score로 변환해야 합니다.**

3. **Corwin-Schultz spread estimator**: OHLC만으로 bid-ask spread 추정. 소형주 liquidity signal로 유의미.

---

## 1. 타겟 설계의 근본 결함: c2c_120 Binary Classification

현재 타겟: `c2c_120 > 0` → class 1, `c2c_120 ≤ 0` → class 0.

**이게 Non-Top200에서 왜 문제인가?**

소형주의 c2c_120 분포는 대형주와 완전히 다릅니다. 대형주는 정규분포에 가까운데, **소형주는 fat tail + 0 근처에 mass가 몰려 있습니다.** 즉:

- 소형주 c2c_120의 50% 이상이 ±0.1% 이내 → **사실상 노이즈**
- 이걸 binary로 자르면 **label의 절반이 coin flip**
- 모델이 학습하는 건 signal이 아니라 **0 근처의 random noise 방향**

AG CLS가 되는 이유? AG는 multiclass로 **magnitude 구간까지 분류**합니다. "0 근처" vs "확실한 상승" vs "확실한 하락"을 구분하죠. Binary CE는 이 구분을 날려버립니다.

**제안**: Dead zone을 도입하세요. `|c2c_120| < threshold` (예: 0.15%)인 샘플은 **학습에서 제외**하거나 별도 class로 분리. 3-class (`down / neutral / up`) 또는 dead zone masking이 binary보다 나을 겁니다.

---

## 2. Loss Function: CE + ListNet λ=0.3의 모순

CE loss는 **"이 종목이 오를까 내릴까"**를 물어봅니다. ListNet은 **"이 시점에서 어떤 종목이 더 많이 오를까"**를 물어봅니다.

**이 두 질문은 Non-Top200에서 충돌합니다.**

- CE: 소형주 A가 +0.01% 올랐으면 "맞았다" (binary correct)
- ListNet: 소형주 A가 +0.01%인데 B가 +2%면 A는 ranking loss에서 "틀렸다"

λ=0.3이 Top200에서 잘 되는 이유는 **200개 종목의 수익률 분포가 균질**해서 ranking이 의미가 있기 때문입니다. **837종목을 한 번에 ranking하면 대형주와 소형주의 수익률 스케일 차이가 ranking을 지배합니다.** 소형주가 ±5% 움직이는 날, 대형주는 ±0.5%입니다. ListNet이 학습하는 건 "소형주를 위에 놓아라"라는 **beta signal**이에요.

**이건 Expert1이 지적한 피처 오염과 같은 뿌리입니다.** 피처가 아니라 **loss function이 beta를 학습시키는 겁니다.**

## 3. 평가 체계의 치명적 결함: Sim ≠ Backtest

실험 기록에서 가장 심각한 발견:

> "Sim CumAlpha와 실제 alpha가 무관"

이건 **실험 파이프라인 자체가 무의미**하다는 뜻입니다.

왜 괴리가 나는지 분석하면:
- **Sim beta**: 837종목 equal-weight mean return
- **Backtest beta**: cap-weighted KOSPI index

이 차이가 Non-Top200에서 극대화됩니다. 소형주 600개가 equal-weight에서는 beta의 대부분을 차지하는데, cap-weight에서는 거의 0입니다. 모델이 "소형주 전체가 오를 때 소형주를 사라"는 signal을 학습하면 sim에서는 alpha로 보이지만 실제로는 **pure beta**입니다.

**이걸 해결 안 하면 아무 실험이나 100개 돌려봐야 의미 없습니다.**

**제안**:
1. Sim의 beta 계산을 **cap-weighted**으로 바꾸거나
2. **유동성 bucket별 beta**를 따로 계산하거나  
3. 최소한 **sim과 backtest의 상관계수**를 먼저 측정해서 sim이 유효한 proxy인지 확인

## 4. H1 (Per-Sample 학습) 비판

Expert1이 H3(temporal z-score)를 최우선이라 했는데, **저는 동의하지 않습니다.**

H1(per-sample TabM)이 되려면 **837종목의 feature 분포가 동질적**이어야 합니다. PLE binning이 스케일을 흡수한다고 했는데, **binning boundary는 전체 데이터에서 계산됩니다.** 소형주 feature의 99th percentile이 대형주의 50th percentile일 수 있어요. 그러면 소형주 데이터의 대부분이 하위 몇 개 bin에 몰리고, 상위 bin은 대형주만 차지합니다.

**이건 PLE binning이 암묵적으로 종목 크기를 인코딩하는 겁니다.** Cross-sectional z-score와 같은 문제가 다른 형태로 나타나는 거예요.

**해법**: Per-stock quantile binning. 종목별로 bin boundary를 따로 계산. 이러면 TabM이 종목 내 패턴만 학습합니다.

- Top200에서 CS-MLP가 되는 게 이걸 증명
- 유동성 bucket = 사실상 **risk factor가 비슷한 종목끼리 묶는 것**

## 4. 아키텍처 관점에서 추가 제안

Expert1, Expert2 모두 피처/타겟/loss를 많이 얘기했는데, **아키텍처 관점에서 빠진 것**이 있습니다:

### A. Stock-Conditional TabM

TabM의 PLE binning은 global boundary입니다. **종목 ID를 conditioning으로 넣으면?**

- 종목 embedding (d=16) → MLP의 각 layer에서 FiLM conditioning: `h = γ(stock) * h + β(stock)`
- 이러면 같은 feature 값이 종목에 따라 다르게 해석됨
- AG의 "종목별 독립 학습"을 **하나의 모델로 근사**하는 셈
- **장점**: 종목 간 공유 가능한 패턴은 공유하되, 종목별 특이성도 포착
- **리스크**: 837개 종목 embedding이 과적합할 수 있음 → dropout 0.5 or embedding dim을 4-8로 제한

### B. Two-Stage: Cluster → Per-Cluster Model

H2(Bucketed CS)의 확장판인데:
1. Stage 1: feature 기반 unsupervised clustering (K-means on rolling feature stats)
2. Stage 2: 각 cluster별 독립 TabM 학습

이건 유동성 기준 버킷보다 **데이터 드리븐**이라 더 자연스럽습니다. 단, cluster assignment가 시간에 따라 바뀔 수 있어서 look-ahead bias에 주의.

## 6. Expert2의 "Sharpe loss" 제안에 대해

**금융 데이터에서 differentiable Sharpe loss는 실무적으로 잘 안 됩니다.** 이유:

1. Sharpe = mean/std인데, **mini-batch에서 std 추정이 noisy** — batch 4096이면 그나마 낫지만 종목×시점 조합이라 시점 당 종목 수가 줄어듦
2. Sharpe는 **non-convex**이고 gradient landscape가 rough — CE보다 최적화가 어려움
3. K200 실험에서 ListNet이 잘 된 이유는 **CE(개별 종목 방향성) + ListNet(상대적 순위)**의 보완성 때문. Sharpe는 이 두 신호를 모두 뭉개버림

**대신 PnL-weighted CE가 더 현실적입니다.** 맞았을 때 수익률이 높은 샘플에 더 큰 weight를 주는 것. 이건 이미 autoresearch 3/17에서 시도한 적 있고, 일부 효과가 있었습니다.

## 4. Researcher1의 Stock-Conditional TabM에 대한 의견

아이디어는 좋은데 **837개 종목 embedding이 실질적으로 학습되기 어렵습니다.** 이유:

- sample_ratio=0.05에서 종목당 평균 데이터: 약 14.9M × 0.05 / 837 ≈ 890 samples
- 890개 sample로 embedding vector를 학습하면 **거의 확실히 과적합**
- embedding dim을 4로 줄여도 종목당 4개 파라미터 × FiLM의 γ, β = 8개 파라미터를 890개로 학습

**대안: 종목 embedding 대신 종목의 "meta-feature"를 conditioning으로 사용.**

- 종목의 rolling 30일 평균 거래대금, 변동성, 시가총액 proxy (없으면 가격 × 거래량) 등 3-5개 연속 변수
- 이건 learnable embedding이 아니라 **관찰 가능한 feature**이므로 과적합 리스크 없음
- FiLM: `h = γ(meta) * h + β(meta)` where `meta = [avg_volume, avg_volatility, ...]`
- **종목이 바뀌어도** 비슷한 특성의 종목이면 비슷하게 처리 → generalization 우수

이 방식이면 Stock-Conditional TabM의 의도(종목별 적응)를 살리면서 과적합 문제를 피할 수 있습니다.

## 5. 시계열 모델이 전멸한 이유 — 아키텍처적 분석

실험 기록을 보면 GRU, Transformer, CNN 등 시계열 모델이 전부 실패했습니다. 이건 **입력이 이미 rolling feature이기 때문**입니다.

153 (또는 105) feature가 이미 `log_diff_close_open_5min`, `vol_per_avg_120min` 같은 rolling 통계량입니다. 즉 **temporal information이 이미 feature engineering으로 추출된 상태**에서 sequence model을 올리면 중복 인코딩입니다. Sequence model이 유의미하려면:

- **Raw OHLCV 시퀀스**(120개 1분봉)를 직접 입력하거나
- **Feature의 시퀀스** (현재 시점 feature가 아니라 과거 N시점의 feature 벡터)를 입력해야 함

하지만 이건 **데이터 파이프라인을 완전히 새로 만들어야** 합니다. 현재 NPY는 (종목, 시점, feature) 형태로 시점 하나에 대한 snapshot이니까요. 이건 Phase 3 이후나 가능하고, 현재 우선순위는 아닙니다.

**결론: 현재 rolling-feature 기반에서는 tabular model(TabM, MLP)이 정답이고, 시계열 모델을 다시 시도하려면 raw sequence 파이프라인이 선행되어야 합니다.** 이건 이번 21일 계획에는 넣지 맙시다.

### 2. Meta-Feature Conditioning — **피처 설계 관점에서 지지하되 경고**

Researcher2가 종목 embedding 대신 `[avg_volume, avg_volatility, price×volume proxy]` 같은 meta-feature를 conditioning으로 쓰자고 했는데, **금융적으로 맞는 방향**입니다. 이유:

- 종목의 "성격"을 인코딩하는 올바른 방법 — learnable embedding은 ID를 외우는 것이고, meta-feature는 **종목의 구조적 특성**을 인코딩
- 새 종목이나 상장 후 특성이 바뀐 종목에도 자연스럽게 적응

**경고: meta-feature의 rolling window가 핵심입니다.**

- `avg_volume_30d`를 쓴다고 했는데, **30일 = 약 11,700분봉**입니다. 이 window가 충분히 길어야 "이 종목의 평균적 성격"을 반영합니다.
- **절대로 같은 날의 평균을 쓰면 안 됩니다.** 장 초반에 거래가 폭증한 날, avg_volume이 높아지면서 conditioning이 바뀌면 → **within-day information leakage** 아니지만, **noise가 conditioning에 직접 전파**됩니다.
- **최소 5일(1주일) rolling, 권장 20일(1개월) rolling**으로 meta-feature를 계산해야 합니다. 그래야 "이 종목은 원래 이런 종목이다"를 안정적으로 인코딩합니다.

---

### 3. VSN (Variable Selection Network) — **피처 redundancy의 올바른 해법**

제가 1차에서 "105feat의 50% 이상이 redundant"라고 했고, PCA로 사전 정리를 제안했는데, **Researcher2의 VSN이 더 나은 접근입니다.** 이유:

- PCA는 linear redundancy만 제거 — 비선형 중복은 못 잡음
- PCA는 **예측과 무관한 분산 방향**을 보존할 수 있음 (가격 스케일 차이 등)
- VSN은 **예측에 유용한 feature만 선택**하도록 end-to-end 학습

**하지만 VSN에 하나 추가해야 할 것이 있습니다.** Feature importance weight를 학습한 후, **어떤 feature가 선택/제거되는지 반드시 로깅**하세요. 이유:

1. 만약 VSN이 `price_diff_raw` 50개를 전부 낮은 weight로 떨어뜨리면 → **이 50개가 진짜 redundant하다는 증거** → 다음 데이터 파이프라인에서 제거 가능
2. 만약 VSN이 `vol_per_avg_360`만 높이고 나머지 vol feature를 다 떨어뜨리면 → **장기 거래량 추세만 유의미** → 단기 vol feature 제거 가능
3. **소형주와 대형주에서 feature importance 패턴이 다르면** → regime-dependent feature selection의 근거

이 로깅이 없으면 VSN은 "성능은 올랐는데 왜인지 모름"이 됩니다. **해석 가능성이 다음 실험 설계의 핵심 입력**입니다.

---

### 4. 남은 피처 체크: Phase 2의 Garman-Klass / Amihud 구현 시 주의

PM이 Phase 2에 `FEAT-1_garman_klass_amihud`을 넣었는데, 구현 시 **반드시 temporal z-score 변환을 적용하라**고 다시 강조합니다.

| 피처 | raw 범위 | 문제 | 변환 |
|------|---------|------|------|
| Garman-Klass vol | 0 ~ ∞ (소형주에서 극단적) | 종목 간 스케일 100배 차이 | **종목별 rolling z-score (window=360분)** |
| Amihud | 0 ~ ∞ (소형주에서 극단적) | 유동성의 inverse이므로 소형주가 극단적으로 큼 | **종목별 rolling z-score + winsorize (3σ clip)** |

Amihud은 특히 **outlier에 취약**합니다. 거래량이 0인 분봉에서 division by zero가 나오므로 `max(volume, 1)` 처리 필수. 그리고 소형주에서 거래 없는 분봉이 50%를 넘을 수 있어서, **Amihud 계산 전에 zero-volume 비율 자체를 별도 feature로 추가**하는 게 낫습니다:

```
zero_vol_ratio_N = count(vol==0 in window N) / N
```

이건 Amihud보다 **더 robust한 illiquidity proxy**일 수 있습니다.

### 5. Survivorship Bias — 아직 답이 없음

1차에서 체크했는데 아무도 답을 안 했습니다. **837종목 중 상폐된 종목이 있는지, train 기간에 상장한 종목이 있는지 확인이 필요합니다.**

- 상폐 종목이 train에 있고 test에 없으면 → train과 test의 종목 구성이 다름 → **label 분포 shift**
- 신규 상장 종목이 test에만 있으면 → 학습에서 본 적 없는 패턴 → 예측 무의미

이건 `offsets.json`을 보면 확인할 수 있습니다. **Phase 1 실험 전에 5분이면 체크 가능하니까, 반드시 선행하세요.**

## 5. 멀티태스크 — 여전히 아무도 안 봤음

제 1차 체크리스트 6번: "c2c_60 + c2c_120 동시 학습이 나은 상황이 아닌가?"

- c2c_120(120분 후 수익률)만 학습하면 모델은 120분짜리 signal만 찾음
- c2c_60(60분)을 auxiliary target으로 추가하면, **60분과 120분에 공통으로 작용하는 factor를 공유 representation에서 학습**
- 금융 데이터에서 이런 multi-horizon learning이 **regularizer 역할**을 함 — 한 horizon에 overfitting하는 걸 방지

**구현은 간단합니다.** Loss = `CE(c2c_120) + α * CE(c2c_60)`. Output head 하나만 추가하면 됩니다. α=0.3 정도면 auxiliary loss가 너무 지배적이지 않으면서 regularization 효과를 줍니다.

**하지만 이건 Phase 3에 넣는 게 맞습니다.** Phase 1에서 TabM per-sample이 되는지부터 확인해야 하니까. 다만 **Phase 3 리스트에 ARCH-4_multitask_c2c로 넣어두세요.**

```
### 실험: ARCH-4_multitask_c2c (Phase 3, 보류)
- 모델: TabM + auxiliary head (c2c_60)
- Loss: CE(c2c_120) + 0.3 * CE(c2c_60)
- 조건: Phase 1-2에서 TabM per-sample이 sim > 0
- 근거: multi-horizon이 overfitting regularizer로 작동
- NPY label: y[:,21]=c2c_120, 추가로 c2c_60 인덱스 확인 필요
```

## 3. Expert2의 Dead Zone Phase 1 편입 — **좋은 아이디어지만 함정이 있음**

"NPY에서 |c2c_120| < 0.15% 행을 제거하면 trainer 수정 없이 dead zone 효과"라고 했는데, **데이터 구조상 문제가 있습니다.**

현재 NPY는 `(종목, 시점, feature)` 형태이고, `offsets.json`이 종목별 start/end 인덱스를 관리합니다. 행을 제거하면:
- offsets가 전부 재계산되어야 함
- 종목별로 제거되는 행 수가 다르니까 offsets가 불규칙해짐
- **기존 eval 코드가 원본 NPY 기준으로 인덱싱**하므로, 학습은 filtered NPY로 하고 추론은 원본 NPY로 해야 함 → 이건 이미 다른 경로를 쓰면 되니까 가능

**그래서 "NPY 전처리로 5분이면 된다"는 과소평가입니다.** offsets 재계산까지 포함하면 30분~1시간. 불가능하지 않지만 "config만 바꾸기"보다는 확실히 품이 듦.

## 5. VSN (Variable Selection Network) — **동의하되 우선순위 조정**

하지만 VSN은 **새 모듈 구현 + TabM 아키텍처 수정**이 필요합니다. Phase 3의 다른 실험(Meta-Feature Conditioning, Multitask)보다 구현 비용이 높습니다. 

**Phase 3 내부 우선순위**:

## 6. Expert2의 Multitask c2c_60 — **금융적으로 합리적**

Multi-horizon learning이 regularizer로 작동한다는 건 학술적으로도, 실무적으로도 지지됩니다. Qlib의 ALSTM+TRA 등에서 multi-horizon auxiliary loss가 효과적이었고, 금융 데이터에서 **한 horizon에 과적합하는 걸 방지**하는 건 실제로 중요합니다.

**다만 c2c_60이 c2c_120과 상관이 너무 높으면** (ρ > 0.8) auxiliary loss의 정보량이 낮아서 효과가 미미할 수 있습니다. NPY label에서 c2c_60의 인덱스를 확인하고, **c2c_120과의 상관계수를 먼저 체크**한 후 Phase 3에서 진행해야 합니다.

더 나은 auxiliary target은 **c2c_30이나 c2c_240** 같은 더 짧거나 더 긴 horizon일 수 있습니다. 120분과 상관이 낮을수록 auxiliary의 regularization 효과가 큽니다.

## 3. Per-Stock Quantile PLE — Phase 1 실패 시 핵심 대안

제가 2차 발언에서 언급한 **Per-Stock Quantile PLE**를 다시 강조합니다. Phase 1에서 TabM이 sim ≤ 0이면, 원인 후보는:

1. ListNet beta 오염 → H1-1a vs H1-1b 비교로 판별
2. PLE global binning의 종목 크기 인코딩 → **이건 H1-1a도 걸림**
3. 105feat 자체의 한계 → H1-3(alpha101)과 비교로 판별

**2번이 원인이면 temporal z-score(H3)로도 해결 안 됩니다.** PLE binning 자체가 문제니까요. 그래서 의사결정 트리에 하나 더:

```
H1-1a, H1-1b 모두 sim ≤ 0
  ├─ H1-1a ≈ H1-1b → ListNet은 무관, PLE 또는 feature 문제
  │    ├─ H1-3 > 0 → feature 문제 (105feat 한계)
  │    └─ H1-3 ≤ 0 → PLE global binning 의심 → Per-Stock Quantile PLE 검토
  └─ H1-1a >> H1-1b → ListNet이 원인, CE only로 진행
```
