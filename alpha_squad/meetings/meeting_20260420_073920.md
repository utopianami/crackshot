**A. Residualize-then-Rank (메인 베이스라인)**

**B. Synergistic Formulaic Alpha Loop (LLM 루프 레버리지)**

## 1. CA-AE characteristic의 시점 오염 — 최대 리스크

`log mcap, 30d vol, funding rate`를 conditioning으로 쓴다고 했는데:

- **`30d vol`**: rolling window endpoint가 `[t-30d, t]`면 정의상 `t` bar close를 포함. 알파 타겟이 `t → t+h` residual이라면 1-bar gap 필수. `[t-30d-1, t-1]`로 시프트 안 하면 CA-AE가 "미래를 예측하는 beta"를 학습합니다.
- **`funding rate`**: 이게 제일 위험. Binance funding은 **8h 주기 realized** vs **실시간 predicted** 두 값이 공존. "시점 `t`의 funding"이 predicted면 이미 `t+8h`까지의 mark price 움직임을 일부 반영 — 명백한 leakage. **사용할 값은 "직전 지급된 realized funding"(`t - (t mod 8h)`)로 고정**하고 conditioning 명세에 적어야 합니다.
- **`log mcap`**: circulating supply 기반인데 token unlock 스케줄은 사전 공개. 이건 leakage 아님. 다만 unlock 이벤트 당일 `log mcap` jump를 feature가 그대로 받으면 regime change가 아니라 **회계 이벤트**를 signal로 학습. unlock 일정 마스킹 필요.

## 2. CS rank 원칙의 **예외**가 필요하다

"모든 size/volume feature는 per-timestep rank"는 맞지만 **funding rate에는 적용 금지**입니다.

근거: funding rate의 알파는 **절대값 극단**에서 나옵니다 (±0.1%/8h 이상에서 mean-reversion). 시장 전체가 high funding인 euphoria 레짐과 모두 낮은 chop 레짐에서 **rank 분포는 동일**하지만 **알파 부호는 반대**. rank로만 보면 regime-conditional signal이 사라집니다.

**대안**: funding은 **`{CS rank, 레짐 내 z-score, 절대 magnitude bucket}` 3채널**로 넣고, CA-AE가 알아서 interaction 배우게 하거나 명시적 product feature로 주입.

## 3. 3-factor residual의 double dipping

Residualize-then-Rank에서 Stage 1이 `market/size/momentum` factor를 빼내는데, Stage 2 iTransformer input에 **`N-bar return`을 그대로 넣으면 momentum factor를 두 번 사용**합니다. residual 학습의 의미가 희석돼요.

**수정**: Stage 2 input은 (a) residualized return, (b) **non-momentum 계열 feature**(microstructure, flow imbalance, funding, basis)로 제한. raw return은 빼거나 "residual 후 rank"로만 넣기.

## 4. Survivorship — dynamic universe라도 위험

"월 1회 갱신 top 50~100"이라도 **과거 delisted 코인**(LUNA, FTT 등)을 학습 유니버스에 포함 안 하면 CS momentum 수익이 크게 과대계상됩니다. 실증적으로 crypto CS momentum의 Sharpe는 survivorship 보정 전후 0.3~0.5 차이.

**수정**: 각 timestamp `t`에 대해 **당시 시점 기준 상장 + top-N** 스냅샷을 raw로 저장. delisted 코인의 delisting 공지 ~ T+3d 구간은 label 마스킹.

## 5. iTransformer variate attention의 숨은 위험

variate-as-token은 **token 수 = 유니버스 크기**. top-N이 **dynamic**이라 batch마다 token 수가 바뀜. padding/masking 처리 잘못하면 attention score가 batch size에 의존해 regime마다 "같은 feature가 다른 표현"이 됩니다. 이것도 sentinel급 collapse 유발 가능.

**체크리스트**: (a) attention mask가 실제 상장 코인만 참여하게 강제, (b) 정규화는 variate dim이 아닌 feature dim, (c) 배치 내 코인 순서 permutation invariant 검증 (unit test).

## 6. 중복 피처 경고

제안 feature grammar `{price, volume, funding, OI, basis, CS-rank}`에서 실전 상관:

- `taker buy ratio` ≈ `CVD slope` ≈ `short-term return sign` — 상관 0.7+
- `OI change` ≈ `basis change` (perp vs spot이 OI flow에 끌려감) — 상관 0.5+
- `Amihud illiquidity` ≈ `1/volume` ≈ `spread proxy` — 거의 동일 정보

**권고**: feature set 확정 전 **일간 correlation matrix + VIF** 찍어서 |ρ|>0.8 또는 VIF>10은 하나만 남기기. AlphaForge LLM 루프 돌리기 **전**에 해야 함 — 안 그러면 루프가 중복 공식만 양산.

## 1. iTransformer 선택은 과한 베팅 — FT-T baseline 먼저

Researcher2가 "PatchTST/TabM은 row-wise라 코인 간 정보가 loss에서만 섞인다 → iTransformer"로 점프했는데, 이 논리에 두 가지 헛점이 있습니다.

- **우리의 sentinel 원인은 architecture가 아니라 feature scale이었음.** KOSPI sentinel은 FT-T가 아니라 **TabM에서만** 발생했고(FT-T 200은 0.05%), 원인은 `trade_value / market_avg`의 raw magnitude가 distribution tail에서 PLE bucket을 소진한 것. **model forward가 bit-identical이 된 건 embedding layer가 saturate된 결과**지 row-wise loss 때문이 아닙니다. 즉 iTransformer로 간다고 해결되는 문제가 아님.
- **Cross-sectional 정보 혼합이 정말 필요한가?** Ranking loss(ListMLE)를 쓰면 gradient 단계에서 이미 섞입니다. iTransformer가 variate attention으로 **표현 공간에서** 섞는 건 **시계열 forecasting**에서 이득이지, 단일 timestamp cross-sectional score 생성에는 **marginal gain이 작고 Expert1 지적한 dynamic variate 리스크는 큼**. ROI가 나쁩니다.

**권고**: Stage 2는 **FT-Transformer + PLE (우리가 이미 safely 학습시켜본 구조)** 부터. 이게 ICIR > 0.5 안 나오면 아키텍처가 아니라 alpha signal 자체를 의심해야 합니다.

## 2. CA-AE는 크립토 horizon에서 부적합 — rolling WLS로 충분

Gu-Kelly-Xiu의 CA-AE는 **US equity 월간 수익률**에 검증된 것이고, `log mcap, book-to-market` 같이 **slowly-varying characteristic**로 beta를 학습합니다. 크립토에서 4~24h horizon 알파를 추출하는데 CA-AE를 쓰면:

- Characteristic도 고주파(`30d vol`, `funding`)여야 해서 beta 자체가 noisy → 2-stage에서 **residual noise가 Stage 2로 그대로 전파**
- N=50~100 좁은 universe에서 K=3 factor를 고정하면 factor identifiability 약함 (rotation invariance)

**대안**: **rolling 7~14d WLS로 BTC/ETH 2-factor beta 시변 추정 → residual return 사용**. 이게 해석 가능하고, CA-AE가 줄 수 있는 marginal gain보다 **비용이 10분의 1**. 나중에 residual의 구조화된 패턴이 확인되면 그때 CA-AE 고려.

## 3. Non-stationarity 대응 — rolling train은 **필수**가 아니라 **default**

크립토는 regime change 빈도(BTC halving, major delisting, funding rate 극단 event)가 equity보다 훨씬 높습니다. 정적 train/val split로 학습시키면 **out-of-sample 첫 월에 성능 폭락이 기본값**입니다. 우리 KOSPI TabM도 이 문제로 4월 retrain 돌린 것 기억하실 겁니다.

**권고**: 시작부터 **rolling window retrain (예: 매주 last 90d로 refit)** 파이프라인을 전제로 설계. 한 번 학습한 모델의 Sharpe는 **report하지 않는다**는 룰을 박아두세요. 크립토 백테스트에서 고정 모델 결과는 거의 항상 overfitted입니다.

---

## 4. 아무도 안 말한 base-rate — 이 전략 성공률

정직하게 짚습니다. Crypto CS momentum의 **survivorship 보정 후 Sharpe는 대부분 연구에서 0.5~1.0, turnover 감안한 net은 더 낮음**. Market-neutral 가정해도 long/short 스프레드가 funding cost(양쪽 누적 ~20~40%/yr)를 넘기려면 **gross IC > 0.05 지속적으로** 필요. 이건 어려운 목표입니다.

**회의 목표를 수정 제안**: "어떤 모델"이 아니라 **"어떤 feature/horizon 조합이 funding cost를 넘을 수 있는지"**부터 검증. Expert1 말대로 feature VIF pre-screening → 단일 feature IC 테이블 먼저. 모델은 그 다음 이야기.

## 수용 (즉시 수정)

### 1. Expert1 leakage 3종 — 전부 수용
- **Funding**: `realized(t - (t mod 8h))`로 고정 명세. predicted 사용 금지.
- **30d vol endpoint**: `[t-30d-1, t-1]`로 1-bar gap.
- **mcap unlock masking**: token unlock 스케줄 `±1d` 레이블 마스크.

### 2. Funding rate는 CS rank 금지 — 수용
Expert1 말이 맞습니다. funding은 **절대 magnitude에 알파**가 있음 (±0.1%/8h mean-reversion). 제가 "모든 size/volume"이라고 한 원칙이 과일반화였습니다. **funding은 `{rank, 30d z-score, signed abs bucket}` 3채널**로 확정.

### 3. Momentum double dipping — 수용
Stage 2 input에서 raw N-bar return 제거. residualized return만 넣거나, raw는 CS rank로만.

### 4. VIF/corr pre-screening을 LLM 루프 **이전에** — 수용
`|ρ|>0.8` 또는 `VIF>10`은 하나만 잔존. AlphaForge grammar는 VIF 통과 feature로만 정의. 이 단계 없이 루프 돌리면 "중복 공식 양산기"가 됩니다. Expert1 지적대로입니다.

### 5. Rolling retrain 필수 (Researcher1) — 수용
주간 refit (last 90d) 파이프라인을 **시작부터** 전제. 고정 모델 Sharpe는 보고 금지 룰 박아두기.

## 부분 반박

### 6. Researcher1 — "iTransformer 과베팅, FT-T부터" → **MVP는 FT-T, iTransformer는 secondary 실험으로 강등**

Researcher1 지적 정확합니다. **sentinel 원인은 row-wise loss가 아니라 feature scale이었음**을 제가 혼동했습니다. iTransformer의 variate attention이 주는 이득은 forecasting에 크고, 단일 timestamp CS score 생성에는 ListMLE gradient가 이미 cross-sectional signal을 주입합니다.

**수정 아키텍처 스택**:
- **MVP (Stage 2)**: **FT-Transformer + PLE** (우리가 이미 안정적으로 학습시킨 구조). 현재 SOTA TabM도 후보로 병행.
- **Ablation**: iTransformer는 **MVP ICIR > 0.3 달성 후** marginal gain 검증용. Expert1의 dynamic variate 리스크(token 수 변동, attention mask)는 그때 unit test로 검증.

단, **TabM은 신중히** — KOSPI에서 sentinel 낸 아키텍처입니다. BTC/ETH가 정확히 dominance 위치이므로 PLE 경계 saturate 재현 가능성 높음. **PLE quantile을 global이 아닌 rolling CS quantile로** 바꾸는 선조치 필요 (제가 최초 발언에서 언급한 원칙).

### 7. Researcher1 — "CA-AE는 horizon 부적합, rolling WLS로" → **MVP는 WLS, CA-AE는 연구 트랙**

Researcher1의 근거(characteristic 고주파화 → beta noisy, N=50~100에서 factor identifiability 약함)에 동의합니다. **비용 대비 기대 gain이 나쁩니다.**

**수정**:
- **MVP (Stage 1)**: **rolling 7~14d WLS로 BTC/ETH 2-factor beta 시변 추정** (해석 가능, 계산 싸고, 검증 쉽다).
- **추가 레이어**: "size neutralize"는 beta 대신 **log mcap quintile 내 rank**로 post-hoc 적용 (Fama-MacBeth 스타일). 3-factor 완전 residualization은 residual의 구조적 패턴이 확인된 후 CA-AE로 확장.

## 이의제기: MODEL-01의 5-class quantile bin은 크립토에 부적합 가능성

## 보강 1: Phase 0에서 비선형 IC도 측정

ALPHA-00이 "단일 feature rank IC" 위주인데, 비선형 alpha (feature interaction, regime-conditional)를 놓칠 수 있습니다. 크립토에서 `funding × OI change`나 `basis × volume`은 개별 IC 0이어도 product/XOR 구조에서 alpha가 생길 수 있음.

## 1. 5-class asymmetric bin 이의제기 — **반대**, listwise로 직행 권고

Researcher2가 `{p10, p30, p70, p90}` asymmetric bin을 제안했는데, 이건 **sample 수 문제**가 심각합니다.

- 유니버스 top 50, weekly rebalance → 각 timestamp의 CS sample 50개
- p90 이상 **5개**, p10 이하 **5개**. bin 내부 label noise 비율이 bin 크기에 반비례 → tail bin CE loss의 gradient 분산이 커짐
- KOSPI top200(per-timestamp ~200 sample)에서 5분위가 작동한 전제 자체가 크립토에 적용 안 됨

**권고**: Phase 1에서 5-class bin을 스킵하고 **바로 listwise loss**(ListMLE)로 진입. Researcher2가 Phase 1.5 ablation으로 미뤄둔 listwise를 **Phase 1 primary**로 승격. Researcher2 본인이 "rank 회귀 + listwise loss (bin 자체 제거)"를 대안으로 언급했으니 내부 정합.

## 2. 비선형/interaction IC 보강 — **지지**, 단 multiple testing correction 필수

VIF 통과 feature 15개면 `C(15,2) = 105` interaction pair. `α=0.05` 순진 검정 시 **expected false positive 5개**. Phase 0 게이트("IC>0.02 feature 3개 이상")가 **순수 noise로 통과 가능**합니다.

- **추가**: **Benjamini-Hochberg FDR correction** (또는 Bonferroni) 명시. "IC>0.02" 대신 `FDR q=0.1 기준 significant한 feature 3개 이상`으로 게이트 재정의
- **추가**: **block bootstrap** (weekly block, e.g. 2주)로 IC 표준오차 추정. 크립토 autocorrelation 무시하고 naive t-stat 쓰면 IC 유의성 2~3배 과대계상

MLP probe IC는 지지. 단 probe 자체의 **train/val split이 Phase 0의 walk-forward와 일치해야** expanding-window leak 방지.

## 3. rolling CS quantile PLE — **지지**, 경계 불연속 리스크 경고

`[t-30d, t-1]` CS quantile bucket 제안에 원칙 동의. 다만:

- **매 timestamp마다 bucket 경계가 이동** → 같은 raw value가 인접 timestamp에서 bucket `k`와 `k+1`을 왕복. PLE embedding의 **quantile boundary discontinuity**가 모델 출력에 jitter 주입
- KOSPI에서 이 문제가 안 드러난 이유는 PLE bucket이 **training set 전체 quantile (정적)**이었기 때문. 동적으로 바꾸면 새 문제 발생
- **완화**: (a) **soft PLE** (두 인접 bucket의 weighted interpolation), (b) **bucket 경계 EMA smoothing** (`α=0.1~0.2`로 경계 자체의 급변 완화), (c) 경계 업데이트 주기를 weekly(rebalance와 동기)로 고정

이 3개 중 (c)가 구현 비용 최저. Researcher2의 Phase -1/0 병행 사전 작업 리스트에 **"경계 업데이트 주기 명세"** 추가 필요.

## 4. funding 3채널의 `signed abs bucket` 정의 미확정

제가 초기에 `{rank, z-score, signed abs bucket}`을 제안했는데 bucket 정의를 안 달았습니다. Researcher2도 그대로 인용만 해서 **명세 공백**이 남아있습니다.

- funding 분포: 평상시 ±0.01%/8h, 극단 ±0.1~0.3%/8h. **log-normal in absolute value**
- **fixed bucket** (e.g. `{0, 0.01%, 0.05%, 0.1%, 0.3%}`): 평상시 90% 샘플이 bucket 0 → 정보 없음
- **quantile bucket**: 극단 magnitude 정보 손실 (쏠림 → 5분위 모두 "극단"으로 표시)
- **권고**: `bucket = sign(funding) × log1p(|funding| / 0.01%)` 연속값 + bucket index 병기. 이건 **연속값 feature**라 PLE가 알아서 처리 — bucket 자체는 사실상 불필요. **funding 3채널을 `{CS rank, 30d z-score, signed log-magnitude}`로 확정** 제안

## 5. Phase 0에 portfolio-level proxy IC 추가 요청

이건 Researcher1의 base-rate 경고에 대한 피처 관점 대응입니다.

- "개별 rank IC > 0.02 feature 3개 이상"이 통과해도 **3개 feature가 강한 상관**이면 combined signal의 marginal gain이 작음. Researcher2의 VIF gate가 이걸 부분 방어하지만 VIF는 선형 상관만 봄
- **Phase 0 추가 산출물**: **top 3 IC feature의 equal-weight rank 평균**을 proxy signal로 만들고 그 signal의 rank IC 측정. 이게 개별 IC의 max보다 **유의하게 높지 않으면** 3개 feature가 redundant
- 계산 비용 거의 0. Go/No-Go 게이트에 "proxy IC > max(individual IC) × 1.1" 추가 제안

## 6. ListMLE JAX 구현 — 단위 테스트 스펙 공백

Researcher2가 Phase -1/0 중 사전 구현 제안했는데, 단위 테스트 명세가 없습니다. 과거 경험상 listwise loss는 다음 2가지에서 조용한 버그 발생 빈도 높음:

- **permutation equivariance**: batch 내 score 순서를 shuffle해도 loss 값 동일해야 함. Equinox `jax.lax.sort` 구현 시 indices 꼬임 빈번
- **tied score handling**: 두 score가 동일할 때 gradient가 deterministic인가 (`jax.numpy.argsort`는 stable sort이나 JIT 하의 behavior 확인 필요)
- **listwise mask**: dynamic universe 대응 — 미상장 코인 자리를 어떻게 masking할지. 이건 Expert1-5(iTransformer dynamic variate)와 같은 패밀리 문제

Phase -1 병행 작업에 "ListMLE unit test 3종 (permutation, tied score, dynamic mask)"을 **명시적 산출물**로 잡아주세요.

## 1. "BTC residual return rank를 5-class로 분류" — 잘못된 질문입니다

회의 전체가 **"prediction → ranking → portfolio"** 파이프라인을 전제하고 있습니다. 이건 KOSPI에서 익숙해진 패턴이지 크립토 long/short alpha-only에 적합한 formulation이 아닙니다.

**근거**:
- KOSPI는 long-only · turnover 제약 약함 · 거래비용 ~5bps. "rank score → top-N"이 자연스러움.
- 크립토 perp는 **양방향 funding cost 25~40%/yr** + **maker/taker fee 양방향 부과** + **rebalance turnover 비용**. 즉 **portfolio Sharpe와 IC 사이의 wedge가 KOSPI보다 한 자릿수 큼**.
- Researcher1이 정확히 짚은 "gross IC > 0.05 지속" 허들은 **IC를 max한 결과로 Sharpe가 나온다는 가정**에서 나온 추정. 이 가정 자체가 깨집니다.

**제안**:
- **Phase 1 loss는 CE도 ListMLE도 아닌 differentiable Sharpe loss** (Lim et al. *J. Financial Markets* 2019, "Enhancing time-series momentum with deep learning")로 직행. portfolio weight를 모델 출력으로 직접 받고 backtest Sharpe를 backprop. 
- 이게 불안정하면 **IC loss + Sharpe regularizer** hybrid (Cong-Tang-Wang-Zhang *RFS* 2021 "AlphaPortfolio").
- Expert1·R2의 ListMLE primary 논쟁이 무의미해지는 게 아니라, **primary는 Sharpe loss / ListMLE는 ablation**으로 우선순위 역전됩니다.

**반론 예상**: "Sharpe loss는 학습 불안정." → 맞습니다. 그래서 R3 phased plan 안에 **Phase 1-A (CE/ListMLE) vs Phase 1-B (Sharpe loss) head-to-head**를 넣자는 게 아니라, **Phase 0 게이트의 정의 자체를 바꾸자**는 겁니다 (다음 항목).

---

## 2. Phase 0 Go/No-Go 게이트 — "IC > 0.02"는 wrong metric

R3가 "개별 rank IC > 0.02 feature 3개 이상 + ICIR > 0.3 1개 이상"을 게이트로 잡았습니다. **이 게이트가 통과돼도 Net Sharpe < 0가 가능합니다.**

**왜 그런가**:
- IC는 cross-sectional rank correlation. **transaction cost와 funding cost를 무시**.
- 크립토 weekly rebalance + dynamic top 50 → 평균 turnover 30~50%/주. 양방향 fee + funding 합산 cost가 알파를 거의 다 먹음.
- 단일 feature IC 0.02 짜리 3개를 등가중 평균해도 **post-cost Sharpe 추정치 없이는 "통과"가 의미 없음**.

**제안 (게이트 재정의)**:
| 항목 | R3 안 | 수정 |
|---|---|---|
| 1차 게이트 | individual rank IC > 0.02 × 3개 | **proxy portfolio (top10/bot10) gross Sharpe > 1.5** + **net Sharpe (funding+fee 차감) > 0.3** |
| 2차 게이트 | ICIR > 0.3 | **Sharpe stability across 4분기 sub-period 모두에서 net Sharpe > 0** (regime robustness) |
| 3차 게이트 | (없음) | **turnover < 80%/week** (그 이상이면 fee가 알파 잠식) |

Expert1이 보강 5번 "portfolio-level proxy IC"를 신규 제안했는데, 거기서 한 발 더 가서 **proxy net Sharpe**여야 합니다. Expert1 제안은 방향은 맞지만 여전히 IC 도메인에 머물러 있어서 부족합니다.

## 3. Multi-horizon multi-task — 누락된 설계 옵션

R3가 ALPHA-00에서 `H ∈ {4h, 8h, 24h}`를 **separate sweep**으로 처리했고, MODEL-01은 best 1개 horizon만 선택합니다. 이건 **two failure modes**가 있습니다.

**Failure mode A**: best H가 단순히 **noise pick**. H=4h가 IC 0.025, H=8h가 0.022면 "4h 선택"인데 standard error 감안하면 둘이 통계적으로 동일.

**Failure mode B**: 정보 손실. 동일 종목·동일 시점에서 **여러 horizon return은 강한 상관 + 미묘한 차이**가 있음. 4h만 학습하면 8h·24h 정보를 버림. Multi-task가 표준.

**근거**:
- Lin et al. *NeurIPS* 2021 "Multi-task Learning for Stock Price Prediction" — 동일 backbone·multi-head로 single-task 대비 IC +20~40% 일관 보고.
- 우리 KOSPI에서도 horizon_indices를 multi-target으로 학습한 trainer 존재 (`primary_horizon` + auxiliary). 이미 검증된 패턴.

**제안**:
- **MODEL-01 자체를 multi-horizon multi-head**로 설계. 3개 head (4h/8h/24h), shared backbone, primary head로 portfolio 구성.
- Loss: `Σ_h w_h · L(score_h, target_h)`, w는 horizon별 IC variance로 inverse weighting.
- Phase 0 ALPHA-00는 horizon별 **단일 feature IC를 포기하지 않고**, 추가로 **3 horizon target의 corr 매트릭스**를 산출. corr > 0.7이면 multi-task로 합쳐서 효율, corr < 0.3이면 **별개 알파라서 각자 학습**이 정답.

## 4. "월 1회 universe rebalance"의 look-ahead 위험 — 누구도 안 짚었음

Expert1이 delisted coin survivorship을 짚었지만, 그 반대 방향 leakage는 누락됐습니다.

**문제**: "월 1회 top 50 갱신"은 **다음 달의 universe를 오늘 시점에 알고 있다**는 뜻. 만약 어떤 코인이 t에 신규 listing됐는데 1달 뒤 top 50에 진입한다면, 우리가 t시점 학습/예측 시 **그 코인을 universe에 포함하면 미래 정보 사용**.

**구체적 함정**:
- "각 timestamp t에서 당시 상장된 dynamic top 50"라고 R3가 적었지만 **갱신 주기가 월 1회**인 한, 갱신 시점 직전 1달 동안 universe가 **frozen**. 그 동안 새로 listing된 coin이 갱신 시점에 top 50 진입하는 경우, 갱신 시점부터 universe에 포함되는 건 OK.
- 진짜 문제는 **delisting 예고**. Binance가 t-7d에 "t시점 delisting" 공지하면, t-7d ~ t 사이에 그 coin은 universe에서 제외돼야 함. 월 1회 갱신은 이걸 못 잡음.

**제안**:
- **Universe membership은 daily 갱신** (cost 거의 0, listing/delisting 공지 즉시 반영). 종목 score 학습/예측만 weekly.
- Delisting 공지 시점부터 short은 강제 청산, long은 hold-to-delisting (보통 t+3d 청산).

## 5. Label noise floor — 다들 무시한 ceiling

크립토 1h~24h horizon은 **SNR 극도로 낮음**. R1이 base-rate 경고했지만 noise floor 자체를 정량화 안 함.

**Roni Israelov 추정 방식 (Israelov & Klein, AQR 2016)**:
- 자산 i의 horizon H 수익률 = `signal_i + noise_i`
- noise_i ~ daily realized vol × √(H/1day)
- BTC 1d realized vol ~3%, 4h vol ~1.5%, signal magnitude (true alpha rank correlation 0.05 → expected return spread)는 ~0.3%
- **SNR ~ 0.2** → **achievable IC upper bound ~ 0.05~0.08** (Grinold's law 변형)

**함의**:
- "individual feature IC > 0.02"는 SNR 한계의 25~40%. **과한 목표는 아님**, 그러나 여러 feature combine 시 ceiling은 0.08 근처. R1의 "Net Sharpe > 0.5" 게이트는 이 ceiling 기반으로는 **타이트하게 가능**한 정도지 여유 있는 목표가 아님.
- **Phase 0에 noise floor 추정 추가** 권고: BTC residual return의 autocorrelation, white-noise null distribution과의 ratio. 이게 없으면 IC 0.02가 "통과 가능한 목표"인지 "이미 SNR 한계 근처"인지 모릅니다.

## 0. Expert1 질문 답변 — PLE bucket jitter의 IC decay 영향

경험적 감각으로 답합니다(KOSPI에서 정량 실험 없음).

- Bucket 경계 ±ε 구간에 sample의 **~10%** 가 분포한다고 가정하면, 매 timestamp bucket 경계 이동 → 그 10% sample의 embedding이 매 step jitter → 모델 output IC decay가 **2~3배 빠르게** 발생. 이건 GBDT에서 split threshold 경계 근처 sample의 prediction instability와 동일 메커니즘 (Wyner et al. *JMLR* 2017 "Explaining the Success of AdaBoost" 논지 재활용).
- Expert1 3안 중 **(c) weekly 경계 동기화 + (a) soft PLE (두 bucket weighted interpolation)** 조합이 안전. (b) EMA는 경계값 자체가 해석 모호(실제 어느 시점 분포의 quantile인가?)라 **비추천**.
- **운영 원칙**: "bucket 경계 업데이트 시점 = rebalance 시점 = retrain 시점" 3자 동기. 시스템 간 불일치가 가장 큰 jitter 원인.

## 1. Expert2-#1 (Sharpe loss primary) — **부분 반박**

Sharpe loss direct backprop 제안에 **방향은 동의, primary 승격은 반대**합니다.

- Differentiable Sharpe loss는 **mini-batch Sharpe를 backprop**하는데, weekly rebalance 전략의 Sharpe는 통상 quarterly rolling으로 정의됨. batch 내 Sharpe estimator의 **분산이 ground-truth와 order-of-magnitude 차이**. 학습 초반 divergence가 금융 ML 실무에서 흔한 failure mode.
- Zhang-Zohren-Roberts (*J.Financial Data Science* 2020, "Deep Learning for Portfolio Optimization")가 정확히 이 문제 때문에 **2-stage: IC/MSE loss로 pretrain → Sharpe loss로 finetune** 구조를 표준화. AlphaPortfolio(*RFS* 2021)도 내부적으로 auxiliary loss가 있음.
- **권고**: Expert2의 "Phase 1-A vs Phase 1-B head-to-head 아님"을 거부. **Phase 1은 CE/ListMLE로 안정 수렴 확인 → Phase 1.5에 Sharpe-loss finetune 단계 추가**. "primary를 Sharpe로"는 실전 수렴성에서 실패 확률 높음.

## 2. Expert2-#2 (Net Sharpe 게이트) — **전면 수용**

이건 제가 base-rate 경고할 때 이미 함의된 내용인데 Expert2가 명시화한 것. 제가 놓쳤습니다.

- R3의 "IC > 0.02 × 3 + ICIR > 0.3"은 **necessary**지만 **not sufficient**. Crypto perp의 funding+fee+turnover cost wedge가 KOSPI 대비 한 자릿수 큼.
- Expert2 제안 그대로: **proxy net Sharpe > 0.3** + **4 sub-period 모두 positive** + **turnover < 80%/week**를 Phase 0 게이트로. Expert1의 proxy IC 제안은 이 게이트에 흡수됨.
- 추가 제안: **turnover penalty 가중은 대칭 아님**. short leg는 funding을 받거나 지불하는데, long leg와 **regime-conditional으로 비대칭**(bull regime에서 long이 funding 지불, bear에서 역전). Phase 0 net Sharpe 계산 시 long/short leg **분리 report** 필수. 합산 Sharpe가 통과해도 한쪽만 작동하면 half-alpha.

## 3. Expert2-#3 (multi-horizon multi-task) — **조건부 수용**

방향 동의, 단 negative transfer 위험 경고.

- Multi-task는 **task correlation에 따라 성능 역전**. Ruder (*arXiv* 2017 survey) / Standley et al. (*ICML* 2020 "Which Tasks Should Be Learned Together"): task corr < 0.3이면 single-task 대비 **IC가 떨어지는 경우가 다수**. Expert2 본인이 "corr > 0.7 / corr < 0.3" 분기를 언급했는데 이걸 **phase 0 산출물로 확정**해야.
- 금융에서 multi-horizon head가 작동하는 조건: **horizon 간 target이 cointegrated**. 크립토에서 4h/8h/24h return은 통상 corr 0.5~0.7 (equity보다 높음, mean-reversion 약한 regime). 이 전제는 **Phase 0 horizon target corr 매트릭스로 검증**하고, corr < 0.4면 multi-task 포기하고 single-task + horizon ensemble로 전환.
- Inverse-variance weighting 명시 필수 (horizon별 SNR 다름).

## 4. Expert2-#4 (daily universe) — **수용**

Delisting lookahead는 제가 R1 초기 발언에서 "2022-05 LUNA / 2022-11 FTX 이벤트 전후 공백"을 물었는데 그 함의가 **reactive universe membership**이어야 한다는 것. Expert2가 정리.

- 구현 비용 낮음. Binance API 일간 상장 리스트 pull → top-50 by 30d avg volume → next day active.
- Delisting 공지 policy: Binance announcement API가 T-7d ~ T-1d 공지 window 통상. 공지 시점부터 universe 제외, 보유 포지션은 hold-to-delist 또는 즉시 청산 2-옵션 backtest 분리 report.

## 5. Expert2-#5 (noise floor) — **수용 + refine**

SNR ceiling 정의는 정확하지만 계산이 조금 느슨합니다.

- BTC **residual** return (2-factor WLS 후)의 vol은 BTC raw vol보다 낮음 (beta로 systematic 흡수). 크립토 individual coin residual 1d vol은 통상 **5~8%** (BTC 3%가 아님). 4h residual vol ~ 2.5~4%.
- Signal magnitude 추정(true alpha rank corr 0.05 → 약 0.3% spread)도 Grinold's law 적용 구체화 필요. **Expert2의 IC ceiling 0.05~0.08 결론 자체는 합리적** (대략 같은 자리수).
- **Phase 0에 noise floor 측정 추가**: (a) BTC residual의 AR(1) coef, (b) white-noise null 대비 spectrum ratio, (c) shuffled-target IC 분포의 95 percentile. 셋 다 계산 비용 거의 0. 없으면 "IC 0.02 = SNR ceiling의 25~40%"인지 "이미 천장 근처"인지 해석 불가.

## 여전히 누락된 것 — long/short leg funding asymmetry (제 신규 제안)

5명 중 아무도 명시 안 한 것: **long/short Sharpe 분리 평가**.

- Binance perp funding mechanism: funding > 0일 때 long이 short에게 pay. 평균 funding은 **구조적으로 > 0** (longs outnumber shorts, crypto bull bias).
- 결과: long leg는 **structural funding cost carrier**, short leg는 **structural funding receiver**. 단, bear regime 또는 funding inversion event에서 역전.
- **회의 합의된 "Net Sharpe > 0.5" 게이트는 long+short 합산**인데, leg-wise로 보면:
  - Long leg net Sharpe < 0 (funding 지불 + fee)이 베이스라인 가능성
  - Short leg가 long을 보조하는 구조

**제안**: Phase 1 평가 산출물에 `{long_only_net_sharpe, short_only_net_sharpe, combined_net_sharpe}` 3셋 분리 표. 만약 combined > 0인데 long < 0이면 **long leg drop → short-only 전략**도 valid alternative로 Phase 1.5 ablation 추가.

# Researcher2 재발언 (Expert2 패러다임 전환 수용 + 아키텍처 재설계)

Expert2의 "5명이 KOSPI mental model에 갇혀있다" 지적은 **맞습니다**. 제가 초기에 iTransformer를 던진 순간부터 "predict → rank → bin → CE" 파이프라인은 암묵적 전제였습니다. Expert2 5건 중 아키텍처 영향이 큰 #1·#3에 대한 제 판단과 Expert1·R1 보강에 대한 수렴을 정리합니다.

---

## 1. Sharpe loss primary (Expert2 #1) — R1 2-stage 안에 **전면 동의**

Expert2 원안(Sharpe loss를 primary)에는 **반대**, R1의 수정안(CE/ListMLE pretrain → Sharpe finetune)에 **동의**합니다.

- Zhang-Zohren-Roberts 2020이 2-stage 표준화한 이유가 정확히 **mini-batch Sharpe estimator variance 문제**입니다. weekly rebalance의 quarterly Sharpe를 batch 내에서 재구성하면 분산이 order-of-magnitude 차이 (R1 지적). 학습 초반 divergence 발생률 실무적으로 30%+.
- 단 Expert2의 핵심 메시지 — "CE vs ListMLE 논쟁은 wrong question" — 은 살립니다. **Phase 1 primary loss가 CE/ListMLE든, 궁극 objective는 portfolio Sharpe**라는 framing이 맞음.

**아키텍처 스택 수정**:

| Stage | Loss | 목적 |
|---|---|---|
| Phase 1 (pretrain) | ListMLE (Expert1 권고로 CE→ListMLE 승격) | 안정 수렴, rank 구조 학습 |
| Phase 1.5 (finetune) | differentiable Sharpe loss (AlphaPortfolio 스타일) | portfolio 관점 objective alignment |
| Phase 1.5 ablation | IC loss + Sharpe regularizer hybrid | finetune 발산 시 fallback |

Expert1의 "listwise primary 승격"과 Expert2의 "Sharpe loss로 직행"이 **2-stage 안에서 공존**합니다.

## 2. Multi-horizon multi-task (Expert2 #3) — **조건부 수용, 아키텍처 설계 공유**

R1의 "horizon corr > 0.4 전제" 조건에 동의합니다. 아키텍처 스펙 구체화합니다.

**제안 아키텍처 (FT-T + multi-horizon head)**:
```
feature_tokens → FT-T backbone (shared)
                 ↓
                 cls_embedding
                 ↓
      ┌──────────┼──────────┐
   head_4h   head_8h   head_24h   (각각 MLP 2-layer)
      ↓          ↓          ↓
   score_4h  score_8h  score_24h
```

- **Loss**: `L = Σ_h w_h · ListMLE(score_h, rank(target_h))`
  - `w_h = 1 / Var(IC_h)` (inverse-variance, Phase 0에서 추정)
  - `w_h` 초기값은 1/3 uniform, 3 epoch 후 IC variance로 갱신
- **Gradient conflict 완화**: PCGrad (Yu et al. *NeurIPS* 2020) 또는 GradNorm. negative transfer 감지되면 즉시 gradient 투영.
- **Primary head 선택**: Phase 0 horizon corr 매트릭스 기반
  - corr > 0.7 → primary = best IC horizon, aux로 나머지
  - 0.4 < corr < 0.7 → primary = 3개 rank의 Borda count (ensemble)
  - corr < 0.4 → **multi-task 포기**, 각 horizon별 별도 모델 (R1 경고 존중)

**Expert1 우려 예상 (dynamic universe)**: multi-head는 per-horizon per-coin score라 dynamic universe mask가 각 head마다 propagate. 이건 구현 복잡도 낮음 (broadcast), iTransformer의 variate-as-token 문제(token 수 자체가 변동)와는 다른 레벨.

## 3. Expert1 보강 수용 (funding 3채널 / ListMLE unit test / rolling CS PLE)

### 3-1. Funding 3채널 확정 — **Expert1 제안 그대로 수용**

`{CS rank, 30d z-score, signed log-magnitude = sign(f) · log1p(|f|/0.01%)}`

`signed log-magnitude`가 연속값이라 PLE가 자체 처리한다는 Expert1 지적 맞습니다. bucket index는 불필요. **3채널 최종 확정**.

### 3-2. 5-class asymmetric bin 제 이의제기 — **Expert1 반박 수용, 철회**

N=50 universe에서 p90 이상 5개 → bin CE gradient variance가 치명적이라는 Expert1 지적이 결정적입니다. 제 asymmetric bin 제안 **철회**. ListMLE 직행으로 대체 (R3 Phase 1.5의 ListMLE를 Phase 1 primary로 승격).

Phase 0 산출물에 "per-feature IC by decile"은 여전히 유지 — multi-horizon head의 inverse-variance weight 계산에 재사용.

### 3-3. ListMLE unit test 3종 — **명시적 산출물화**

Phase -1/0 병행 작업의 ListMLE JAX 구현에 **동시 작성**:

1. **Permutation equivariance**: `ListMLE(shuffle(scores, π), shuffle(targets, π)) == ListMLE(scores, targets)` — tolerance 1e-6
2. **Tied score gradient**: 두 score가 bit-identical일 때 gradient 동일 (JIT stable sort 확인)
3. **Dynamic mask**: `mask=[1,1,0,1,0]` 상태에서 masked position의 gradient = 0, 비-masked subset의 loss가 standalone 호출과 일치

이 3종을 `tests/training/losses/test_listmle.py`로 산출물 명시. 미통과 시 Phase 1 진입 차단.

### 3-4. rolling CS quantile PLE — **Expert1의 (c) weekly 동기화 + R1의 soft PLE (a) 조합**

R1이 Expert1의 (c)를 "운영 원칙(bucket 경계 업데이트 = rebalance = retrain 3자 동기)"으로 승격했습니다. 전면 동의.

추가로 **soft PLE (a)** 병행 제안: 두 인접 bucket의 weighted interpolation. R1이 (b) EMA는 "경계값 해석 모호"로 비추천했고, (c) 단독으로는 boundary jitter 완전 해소 안 됨 (weekly 시점 경계 교체 순간 jitter). (a)+(c) 조합이 jitter 최소화.

**산출물**: `src/features/ple_soft.py` — soft PLE 구현, unit test는 "경계값 근처 sample의 embedding이 두 bucket embedding의 smooth interpolation" 검증.

## 4. R1의 long/short leg 분리 평가 — **아키텍처 함의 있음, 수용**

R1의 신규 제안(leg-wise Sharpe 분리)은 평가 지표로 보이지만 **아키텍처에도 영향**.

- 만약 long leg가 structural funding carrier라면, 모델이 "top을 맞추는 것"과 "bottom을 맞추는 것"의 **utility가 다름**. ListMLE가 top/bottom을 대칭으로 취급하는 반면 실전 utility는 비대칭.
- **대응 가능한 아키텍처 옵션**:
  - (a) **asymmetric listwise loss**: top-k ranking loss (e.g. NDCG@k) + bottom-k ranking loss 가중합, weight는 leg별 expected funding cost로 설정
  - (b) **dual-head**: long-selection head와 short-selection head를 분리, 각자 binary classification. multi-horizon multi-head와 직교하므로 head = 2 × 3 = 6개
- Phase 1 primary는 (a) 먼저 (구현 간단). (b)는 Phase 1.5에서 leg Sharpe 비대칭이 심할 때 ablation.

## 5. 제 역할 재평가

Expert2의 메타 코멘트에 솔직히 답합니다. 제 초기 발언(iTransformer + CA-AE)은 **"SOTA 아키텍처로 문제를 이긴다"** 패러다임이었고, 이게 정확히 Expert2가 우려한 KOSPI mental model의 변형(model-first)입니다. 

이번 라운드 합의:
- **아키텍처는 FT-T baseline + multi-horizon head로 단순화**
- **데이터 feasibility (Phase -1) → alpha existence + net Sharpe gate (Phase 0) → 모델 (Phase 1)** 순서 고정
- **Secondary 트랙(iTransformer, CA-AE, AlphaForge)은 Phase 1 통과 후 증거 기반 선택**

제 기여 영역은 "어떤 backbone/head/loss이 fair evaluation을 가능하게 하는가"로 좁혀집니다. "이 문제가 해결 가능한가"는 Expert1·R1·Expert2 영역. **이 분리가 이번 회의의 가장 큰 성과**라고 봅니다.

## 1. R2의 A1 ListMLE unit test — **"target ties" 케이스 누락**

R2가 제 3종(permutation / tied **score** / dynamic mask)을 수용했는데, **target 측 ties**는 빠졌습니다.

- 크립토 N=50 universe에서 `target = BTC-residual return CS rank`는 **float tie 거의 없음** (연속값)이지만, 결측 처리(예: 상장 직후 거래량 부족 코인) 후 rank 매기는 방식에 따라 **tied rank 발생 가능** (동일 rank 부여 or index 기반 tiebreak).
- ListMLE는 target이 strict total order일 때 well-defined. **tied target이 들어오면 loss가 target 입력 순서에 의존** (permutation-variant). 조용한 편향 버그.

**추가 unit test (A1에 덧붙임)**:
4. **Target ties**: 두 position의 target이 동일할 때, 그 두 position을 swap해도 loss 변화 < 1e-6. 실패 시 target ties 발생 가능성 있는 파이프라인(rank 결측 후보)을 원천 차단.

## 2. R2의 A2 Soft PLE — **normalization 적용 순서가 미정**

funding의 `signed log-magnitude = sign(f) · log1p(|f|/0.01%)` 변환 + soft PLE 조합에서 **순서**가 명세 안 됐습니다.

- **Option α**: `log-magnitude → rolling CS quantile PLE bucket` (연속값 변환 후 PLE)
- **Option β**: `raw funding → rolling CS quantile PLE` (log 변환 생략, PLE가 비선형 흡수)

Option α가 정석입니다 (log 변환이 tail을 압축해서 quantile이 informative해짐). β는 평상시 90% sample이 bucket 0~1에 몰려 정보 손실. **A2 산출물에 "PLE 입력은 변환 후 값"을 명시**.

**동일 이슈 적용 feature**: `Amihud illiquidity` (이미 |r|/volume 형태로 skewed 분포), `realized vol` (log 변환 통상), `OI change`(%), `volume z-score`. 모두 **변환 → PLE** 순서 강제.

## 3. R2의 A3 multi-horizon inverse-variance weight — **horizon별 noise floor 차이 미반영**

R2가 `w_h = 1/Var(IC_h)`로 weight 부여하는데, Expert2/R1이 지적한 **noise floor가 horizon마다 다름**이 반영 안 됐습니다.

- 4h horizon: SNR 0.15~0.2, IC ceiling ~0.08
- 24h horizon: SNR 0.3~0.4, IC ceiling ~0.12 (noise accumulation이 덜해서 ceiling 높음)
- Inverse variance 순진 적용 → **4h가 noise 많으니 weight 작아짐** → 맞는 것 같지만, **4h에서 달성한 IC 0.05가 ceiling 대비 62%, 24h 0.06이 ceiling 대비 50%**면 **4h가 더 informative한 horizon**.

**수정 제안**: `w_h = IC_h / noise_floor_h` (ceiling-normalized). 단순 IC·variance 비율이 아니라 **ceiling 대비 활용도**로 가중. Phase 0 noise floor 산출물(shuffled-target null)이 있으면 바로 계산 가능.

## 5. Feature 간 leakage 교차점검 — Top-3 feature combine 시 hidden leak

Expert1 초기 발언 leakage 7종은 **개별 feature** 차원이었습니다. 하지만 Phase 0 출력의 **combined proxy portfolio**에서 발생하는 leak은 별도로 점검 필요:

- **Example**: feature A = `realized vol 4h (1-bar gap 적용)`, feature B = `Amihud 4h (1-bar gap 적용)`. 개별은 safe. 그런데 B 분자에 realized vol이 **implicit**하게 들어가 있음 (`|r|/volume` ≈ `vol·√dt / volume`). A·B 상관 높음 → VIF gate 잡힘. 여기까진 OK.
- **진짜 문제**: A·B가 같은 1분봉 block의 realized path에 공통 의존 → 특정 분봉이 **outlier이면 A·B 모두 동시 오염**. VIF는 이걸 못 잡음 (linear correlation은 낮을 수 있음). 특정 high-vol event에서 두 feature의 residual이 같은 방향으로 튀어서 proxy IC 과대계상.
- **탐지**: Phase 0에서 **feature residual (각 feature를 나머지로 regress한 잔차)의 pairwise autocorrelation 검사**. `|corr(residual_A, residual_B)| > 0.3`이면 물리적 공유 signal 의심.

Phase 0 산출물에 **feature residual correlation matrix** 추가 (VIF 이후 한 번 더). 비용 O(N²·T), 여전히 무시 가능.

## 남은 근본 질문 1: "왜 BTC residual인가"를 아무도 안 물음

회의 전체가 `alpha_i(t, H) = ret_i(t, t+H) - beta_i · ret_BTC(t, t+H)`를 **주어진 것**으로 취급했습니다. 이 target 선택 자체가 한 번도 심판대에 오르지 않았습니다.

**왜 문제인가**:

| 대안 | 장점 | 단점 |

| BTC residual (현재 안) | dominance 단순, 해석 명확 | BTC 자체가 alt 들의 beta carrier 아닌 regime 다수 (ETH-led, SOL-led, memecoin-led) |

## 남은 근본 질문 2: Regime conditioning이 회의에서 조용히 사라짐

**왜 중요한가 (금융 관점)**:
- 크립토는 **regime-conditional alpha가 KOSPI보다 훨씬 강함**: 동일 feature가 bull에서 momentum, bear에서 mean-reversion으로 작동 부호 뒤집힘 (Dobrynskaya RFS 2021이 정확히 이 점).

**제안**:
- **Phase 0 산출물에 "regime split IC" 추가**: BTC rolling 30d realized vol의 median으로 high/low vol regime 양분. 각 regime 내 feature IC 별도 산출.

- **만약** regime split IC가 unconditional IC와 거의 동일하면 현재 합의안 유지, regime 논의 완전 폐기.

## 0. Expert2 직접 요청 답변 — Regime vol 경계값: **median 채택, tertile 비추천**

|---|---|---|---|
| Median 양분 | sample balance 완벽 (각 50%), 통계 검정력 최대화 | 전환구간 ambiguity | ✅ 채택 |

| ❌ skip | sector residual | sector 정의 subjectivity + universe 50개에서 sector당 5~10개 → residual SE 과대. Phase 1.5 ablation 후순위 |

**3종 ablation**: 계산 비용 3배, 결정적 정보는 모두 포함. mcap-index가 승자면 **Liu-Tsyvinski 가정의 horizon 일반화 실패**를 실증.

**구현 주의**: mcap-weighted index는 **circulating supply × price**로 구성 (fully diluted 금지 — unlock schedule 노이즈). Binance 제공 mcap이 없으면 CoinGecko API. Expert1의 "mcap unlock mask" leakage 체크가 여기서도 필요.

## 2. Regime Conditioning (Expert2 #2 근본 질문) — **수용, 단 모델 gating 의무화는 반대**

Expert2가 "agenda에서 증발" 지적은 맞고, Phase 0 **regime split IC** 산출은 **반드시 추가**해야 합니다.

**단 Expert2의 "regime 간 IC 부호 반전 feature 있으면 MODEL-01에 regime gating feature 추가 의무화"는 과도**:

- Regime gating을 모델 입력에 추가(BTC vol quintile)하는 것과, **각 regime별 별도 모델 학습**하는 것은 완전히 다른 설계. 전자는 **단일 모델이 gating feature의 interaction을 학습해야** 하는데, 크립토 weekly rebalance + 3년 데이터면 **regime 전환 샘플 수 부족** (bull 2021, bear 2022, recovery 2023, bull 2024 — 3~4회 전환). 모델이 interaction 학습 못하고 gating feature를 무시할 가능성 높음.
- **대안 (ROI 순)**:
  - **Tier 1 (Phase 0 판정용)**: regime split IC만 산출. **진단 목적**.

  - **Tier 3 (Phase 1.5)**: Tier 2가 단일 모델 + gating feature보다 성능 좋으면, 그때 gating feature 추가 실험.
- Expert2의 "의무화"를 **Tier 2 조건부**로 수정.

## 3. Expert1 Ceiling-Normalized Weight `w_h = IC_h / noise_floor_h` — **지지, 단 weight 범위 cap 필수**

Expert1의 "horizon별 noise floor 반영" 지적은 정확합니다. 제 inverse-variance 원안은 "noise 많은 horizon은 weight 낮게"만 고려, "ceiling 대비 활용도"는 빠졌습니다.

**단 raw ceiling-normalized weight는 실전 수렴 불안정**:
- `IC_h`가 Phase 1 초반 epoch에서 **음수 또는 0 근처**일 가능성 → weight가 음수 또는 발산.
- **완화**: `w_h = max(0, IC_h) / noise_floor_h`, 추가로 `w_h ∈ [0.1, 0.7]` clipping (어떤 horizon도 완전히 dead 아니고, 어떤 horizon도 dominate 못하게).
- epoch 3~5 warmup까지는 **uniform 1/3 고정** → 그 후 running IC estimate으로 ceiling-normalized weight 갱신.

**수정 공식**: 
```
w_h(epoch) = {
  1/H                                    if epoch < 5 (warmup)
  clip(max(0, IC_h) / ceiling_h, 0.1, 0.7) / normalizer   otherwise
}
```

R2의 A3 구현 시 이 공식으로 확정. PCGrad는 gradient 단계에서 conflict 처리, weight는 loss 단계에서 importance — 두 메커니즘 직교하므로 동시 사용 가능.

## 4. 제가 여전히 답 못하는 2건

솔직히 남깁니다.

1. **mcap-index residual의 winner 시나리오에서 factor 구조 재설계 방향**: mcap-index가 BTC+ETH 2-factor를 이기면, 그건 "alt 전체의 systematic이 BTC+ETH로 포착 안 됨"이라는 뜻인데, 그 경우 PCA-based latent factor로 가야 할지 sector factor로 가야 할지 **데이터 보기 전엔 논리만으로 결정 불가**. Phase 0 결과 보고 다음 회의.
